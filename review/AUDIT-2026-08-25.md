# Review-queue audit, 2026-08-25

Every one of the 372 pending candidates was read against three things: the source
excerpt the record itself carries, what the chemistry and geometry physically
allow, and the rest of the library. 336 were promoted into `contrib/cells/`.
36 were held back and carry a comment on their issue explaining why.

Nothing here overrides `docs/07-candidate-review.md`. The checkbox remains the
accept control; this pass is a bulk application of the same judgement, staged on
a branch so the whole set can be read as one diff before it becomes library data.

---

## 1. What was checked

| Check | What it catches |
|---|---|
| Value present in its own excerpt | A locator that cannot support the number it is attached to |
| Voltage ordering and chemistry window | `nominal` outside `absolute_min..absolute_max`; a 3.7 V figure on an LFP cell |
| Temperature ordering and range | min above max; limits outside -60..150 °C |
| Percentage range | efficiency or retention outside (0, 100] |
| Cycle life | above 10,000, or 6,000+ with no depth of discharge, rate or temperature |
| Geometry against the model designation | a CR2032 whose diameter is not 20 mm, an 18650 that is not 18 mm |
| Specific energy and energy density | capacity x voltage over mass and over enclosed volume, per chemistry class |
| Bulk density | mass over enclosed volume outside 0.8-6.0 g/cm3 |
| C-rate | current ratings against the capacity in the same record |
| Internal resistance | R against what the format physically measures |
| Duplication | uid, normalized identity, same-source identical specification sets, cross-maker twins |

The plausibility bands are class-aware: a pack is not judged against cell-level
energy density, a silver-oxide button is not judged against a lithium coin cell,
and cylindrical LFP is not judged against prismatic LFP.

## 3. Duplication: 106 records nothing in the data tells apart

This is the finding that most needs a decision, and it is **not** a set of
duplicate imports — every one is a distinct manufacturer order code. The problem
is that the attribute the order code encodes is not recorded anywhere in the
record, so 106 accepted records are, as data, indistinguishable from a sibling.

| Maker | Records | What separates them in reality | Recorded? |
|---|---:|---|---|
| Renata | 100 | Tab and terminal configuration (`FH`, `HF`, `FV`, `VF`, `RH`, `HR`, `RV`, `AH`, `SM`, and numbered sub-variants) | no |
| Maxell | 6 | `SW` vs `W` = low-drain vs high-drain silver oxide; `HR` vs `HRS` | no |

The largest single group is 19 records — `CR2032 MFR AH`, `AH0`, `AH1`, `FH`,
`FH0`, `FH1`, `FH2`, `FV`, `HF`, `HF0`, `HF1`, `HF2`, `HF3`, `HF4`, `HR2`, `RH2`,
`SM`, `VF`, `VF3` — each asserting 225 mAh and 3 g from the same page, with
nothing else to compare on. 22 more groups of 2-7 follow the same shape.

Three ways to resolve it, in order of how much they preserve:

1. **Record the differentiator.** Add the tab/terminal type (and the Renata
   dimensional drawing it belongs to) as a product attribute. The records become
   genuinely distinct and stay separately orderable — which is what a buyer needs.
2. **Collapse to the base cell** and keep the order codes as `aliases`. Loses the
   ability to answer "which tab styles exist", keeps one row per electrochemical cell.
3. **Leave as is.** Defensible — they are real part numbers — but any query that
   groups by specification returns 19 rows where a user expects one.

**Decided: option 1.** The 106 records stay as separate products in this commit,
and the differentiating attribute is follow-up work — the tab/terminal code for
the Renata parts, the drain class (`SW` low-drain vs `W` high-drain) for the
Maxell silver-oxide pairs, and whatever `HRS` adds over `HR`. Until that lands,
these records are distinguishable by `model_number` alone.

**Not duplicates, checked and cleared:** Panasonic `BR1225`/`BR1225A`,
`BR1632`/`BR1632A`, `BR2330`/`BR2330A`, `CR2032A`/`CR2032B`, `CR2050A`/`CR2050B2`
all differ in recorded maximum operating temperature (85 vs 125 °C, 125 vs 120 °C).
`Maxell CR1632` and `Panasonic Energy CR1632` are identical because IEC coin cells
are standardised across makers. EEMB records sharing a capacity and mass across
different size codes (`LP103042`, `LP503759`, `LP703450`) are different cells with
similar internal volume.

## 6. Why this was staged as a branch rather than 336 checkbox ticks

`approve-candidate.yml` works — the marker is present in every candidate issue
body, and #431 is a worked example. But it runs under
`concurrency: candidate-library-promotion`, and GitHub keeps only one *pending*
run per concurrency group: a rapid series of ticks cancels the queued runs, so
most approvals would silently do nothing and each surviving one would add its own
commit to the default branch.
